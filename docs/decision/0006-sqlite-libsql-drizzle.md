# ADR-0006: SQLite through libSQL and Drizzle ORM

- Status: Accepted
- Date: 2026-11-15

## Context

Single-user and local (ADR-0002) means an embedded database is enough. We need typed queries, migrations, and full-text search (FTS5) for retrieval in Phase 2 and later. The machine cannot compile native modules right now: the Xcode license is not accepted, so `better-sqlite3` may fail to build.

## Decision

- **SQLite via `@libsql/client`.** It ships prebuilt binaries and supports FTS5. It can point at a remote libSQL or Turso URL if ever needed.
- **Drizzle ORM** for the schema (`packages/db/src/schema`) and queries.
- **Migrations** are generated by `drizzle-kit generate` into `packages/db/drizzle/` and committed. The app applies them on first use (`getContainer()` calls `migrateDb`).
- Timestamps are stored as integer epoch milliseconds.
- IDs are random UUID text, using branded TypeScript types.
- Only `@thoth/db` imports Drizzle. Everything else uses repository ports (ADR-0004).

## Consequences

- There are no native build steps, and `:memory:` databases make fast tests.
- The libSQL client is async, so every repository method returns a Promise. That fits the ports anyway.
- `migrateDb` needs an explicit migrations path because bundlers rewrite `import.meta.url`.

## Alternatives considered

- `better-sqlite3`. Synchronous and fast, but a native build risk on this machine.
- Node's built-in `node:sqlite`. Drizzle support was not mature.
- Postgres. Unneeded operational weight for one local user.
